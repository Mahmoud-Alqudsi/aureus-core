# Aureus ERP Database Schema Conventions

## Purpose
[VERIFIED]

It analyzes the physical schema layer across root migrations (`database/migrations/`) and 28 Webkul domain plugins (`plugins/webkul/*/database/migrations/`), detailing naming standards, primary keys, foreign key behaviors, index strategies, flexible data storage, and migration organization.

## Primary Key Conventions
[VERIFIED]
Primary key definitions across Aureus ERP adhere to explicit architectural patterns:

1. **Standard Domain Entity Tables (197 tables with standard id)**:
   - **Pattern**: 197 standard ID tables:
     - `$table->id()`: 194 tables
     - `$table->id('id')`: 1 table
     - `bigIncrements('id')`: 2 tables (Spatie roles and permissions)
   - **Physical Type**: Laravel `$table->id()` creates an auto-incrementing BIGINT primary key abstraction whose physical implementation depends on the database engine. MySQL uses AUTO_INCREMENT while PostgreSQL uses BIGSERIAL/identity-style sequences.
   - **Usage**: Applied to all primary domain entities, master records, transaction headers, and detail lines.

2. **Pure Pivot & Associative Tables (65 tables without standard id)**:
   - **Pattern**: The 65 without standard id include:
     - composite primary key framework tables
     - junction/pivot tables
     - plugin relation tables

3. **Framework Storage Tables**:
   - **Pattern**: String-based primary keys defined by Laravel core:
     - `sessions.id`: `varchar(255) primary key`
     - `cache.key`: `varchar(255) primary key`
     - `job_batches.id`: `varchar(255) primary key`

4. **UUID / ULID Usage**:
   - **Status**: [VERIFIED]
   - UUID usage is limited to framework/system tables. Notable examples include failed_jobs.uuid and notifications.id, where notifications.id is defined as a UUID primary key.

## Foreign Key Conventions
[VERIFIED]
Aureus ERP enforces relational integrity heavily at the database layer. A total of **1016 foreign keys** are defined across creation and alteration migration files.

### Foreign Key Construction Styles
1. **Modern Fluent Syntax (Dominant)**:
   ```php
   $table->foreignId('partner_id')
       ->nullable()
       ->constrained('partners_partners')
       ->nullOnDelete();
   ```
2. **Explicit Blueprint Syntax**:
   ```php
   $table->unsignedBigInteger('company_id')->nullable();
   $table->foreign('company_id')
       ->references('id')
       ->on('companies')
       ->cascadeOnDelete();
   ```

### Standard Column Naming Patterns
- **Company Tenancy**: `company_id` (references `companies.id`)
- **Ownership & Audit**: `creator_id`, `user_id`, `assigned_to` (references `users.id`)
- **Partner / CRM**: `partner_id`, `partner_invoice_id`, `partner_shipping_id` (references `partners_partners.id`)
- **Parent Hierarchy**: `parent_id` (self-referencing table hierarchy, e.g. `categories.parent_id`, `employees.parent_id`)
- **Cross-Plugin Domain Links**: `currency_id` -> `currencies`, `category_id` -> `products_categories`, `order_id` -> `sales_orders` / `purchases_orders`, `move_id` -> `accounts_account_moves`, `operation_type_id` -> `inventories_operation_types`

### Database Foreign Keys vs. Eloquent Relationships
> [!IMPORTANT]
> Database foreign keys enforce physical referential integrity in MySQL/PostgreSQL. Eloquent relationships (`belongsTo`, `hasMany`) are PHP ORM runtime constructs. In Aureus ERP, while standard relational associations have corresponding database foreign keys, polymorphic relationships (e.g. `messageable_id`) and dynamic cross-plugin relations (`resolveRelationUsing`) rely on application-level integrity.

## Nullable Column Patterns
[VERIFIED]
Nullable columns in migrations represent optional associations, draft transaction states, or system-level ownership boundaries:

| Column Pattern | Nullable Occurrence | Physical Meaning | Business / Model Context |
| :--- | :--- | :--- | :--- |
| `company_id` | Nullable on shared/master tables (e.g. `products_products`, `activity_types`); Non-nullable on ledger records (e.g. `manufacturing_orders`, `sales_orders`) | Physical row can exist without a foreign company reference when shared globally | Allows global shared master templates; ledger transactions strictly require company binding |
| `creator_id` / `user_id` | Nullable | Record created without authenticated user or assigned representative | System-generated transactions, background queue imports, or unassigned tasks |
| `partner_id` | Nullable | Optional commercial partner linkage | Direct inventory adjustments, internal transfers, or draft requisitions |
| `parent_id` | Nullable | Self-referencing parent node | Represents top-level root entities in hierarchical trees (categories, departments, accounts) |
| `date_deadline` / `confirmed_at` | Nullable | Timestamp not yet occurred | Workflow state milestones not yet reached |

> [!NOTE]
> A column's `nullable()` status in the database does not dictate business validity. Application Form Requests and Filament resource validation rules determine whether a field is required during user input.

Total: 1016 foreign keys

### Database Hard Deletes vs. Eloquent SoftDeletes
- **Database Delete Rules (`ON DELETE ...`)**: Only triggered when a row is physically removed (`DELETE FROM ...`) or via `forceDelete()`.
- **Eloquent SoftDeletes**: Sets `deleted_at = NOW()` and does not invoke database-level cascade triggers. Child records remain active in the database unless model-level deleting event listeners cascade soft deletes.

## Timestamp and Soft Delete Conventions
[VERIFIED]

### Timestamps (`created_at`, `updated_at`)
- **Adoption**: **191 tables with timestamps** define `$table->timestamps()` or `$table->timestampsTz()`.
- **Omission**: Pure pivot tables (e.g. `user_team`, `plugin_dependencies`, `sales_order_line_taxes`) and framework buffer tables omit timestamps to minimize overhead.

### Soft Deletes (`deleted_at`)
- **Adoption**: **61 tables with soft deletes** define `$table->softDeletes()` or `$table->softDeletesTz()`.
- **Where Common**: Transaction headers (`sales_orders`, `accounts_account_moves`, `purchases_requisitions`, `manufacturing_orders`), core masters (`users`, `products_products`, `partners_partners`, `employees_employees`, `recruitments_applicants`, `maintenance_equipments`, `companies`, `calendars`, `activity_types`).
- **Where Omitted**: Detail lines (`sales_order_lines`, `accounts_account_move_lines`), pivot tables, and log tables (`email_logs`, `chatter_messages`).

## Index and Constraint Conventions
[VERIFIED]
Aureus ERP employs targeted indexing strategies in migration files:

### 1. Unique Constraints
- **Single-Column Unique**: `users.email`, `sequences.code`, `custom_fields.code`, `products_packagings.barcode`.
- **Composite Uniqueness (Multi-Tenant & Pivot)**:
  - `plugin_dependencies`: `$table->unique(['plugin_id', 'dependency_id'])`
  - `user_team`: `$table->unique(['user_id', 'team_id'])`
  - `accounts_tax_groups`: `$table->unique(['company_id', 'name'])`
  - `sequences`: `$table->unique(['company_id', 'code'])`

### 2. Standard Performance Indexes
- **Foreign Key Indexes**: Foreign key indexing behavior depends on the database engine. MySQL/InnoDB may automatically create indexes for foreign key constraints, while PostgreSQL does not automatically create separate indexes. Explicit indexes and composite indexes should be defined where query performance requires them.
  - State & Status fields: `sales_orders.state`, `accounts_account_moves.state`, `inventories_operations.state`.
  - Date lookups: `sales_orders.date_order`, `accounts_account_moves.date`.

Evidence:

## Enum and Type Casting Patterns
[VERIFIED]
Aureus ERP adheres to a strict convention for enum storage across migrations and models:

1. **Database Storage**: Native database enums are used selectively. The repository contains 19 enum columns across specific migrations, while string columns with PHP backed Enum casting remain the dominant convention. Verified locations: users.resource_permission, time-off plugin leave tables.
2. **ORM Casting**: Type safety, validation, and domain state logic are enforced exclusively through PHP 8 backed enums via Eloquent `$casts` or `casts(): array`.

Examples:
- `sales_orders.state` (string) -> `Webkul\Sale\Enums\OrderStatus::class`
- `accounts_account_moves.state` (string) -> `Webkul\Account\Enums\MoveState::class`
- `products_products.type` (string) -> `Webkul\Product\Enums\ProductType::class`
- `inventories_operations.state` (string) -> `Webkul\Inventory\Enums\OperationState::class`
- `time_off_leaves.state` (string) -> `Webkul\TimeOff\Enums\LeaveStatus::class`
- `recruitments_applicants.status` (string) -> `Webkul\Recruitment\Enums\ApplicantStatus::class`

Rationale:
Storing states as strings avoids database-level `ALTER TABLE ... MODIFY ENUM` migration locking issues on MySQL and PostgreSQL, enabling seamless addition of new enum cases in PHP code.

Evidence:
- `plugins/webkul/sales/database/migrations/2025_02_05_053212_create_sales_orders_table.php` (`$table->string('state')`)
- `plugins/webkul/sales/src/Models/Order.php` (`'state' => OrderStatus::class`)

## Polymorphic Schema Patterns
[VERIFIED]
Polymorphic associations allow one table to reference records across multiple target entity types:

| Table | Macro Used | Generated Columns | Purpose |
| :--- | :--- | :--- | :--- |
| `chatter_messages` | `$table->morphs('messageable')` + `$table->morphs('causer')` | `messageable_type`, `messageable_id`, `causer_type`, `causer_id` | Audit trails, messages, and activity logging on any model using `HasChatter` |
| `chatter_attachments` | `$table->morphs('messageable')` | `messageable_type`, `messageable_id` | Universal file attachments linked to any chatter entity |
| `chatter_followers` | `$table->morphs('followable')` | `followable_type`, `followable_id` | User/Partner subscriptions on domain records |
| `sequences` | `$table->nullableMorphs('scope')` | `scope_type`, `scope_id` | Custom prefix sequence generators scoped to specific entities |
| `notifications` | `$table->morphs('notifiable')` | `notifiable_type`, `notifiable_id` | Laravel database notification routing to users or partners |
| `personal_access_tokens` | `$table->morphs('tokenable')` | `tokenable_type`, `tokenable_id` | Laravel Sanctum API authentication tokens |

### Database Integrity Limitation
Because polymorphic relationships store PHP class names in `*_type` columns, RDBMS engines cannot enforce foreign key constraints on `*_id`. Integrity is managed exclusively at the application layer via model lifecycle events (e.g. `HasChatter` cleaning up orphaned attachments).

## Migration Organization Conventions
[VERIFIED]
Migrations in Aureus ERP follow modular ownership boundaries:

1. **Root Migrations** (`database/migrations/`):
   - Own core Laravel tables (`users`, `cache`, `jobs`, `sessions`, `notifications`, `personal_access_tokens`, `permissions`, `settings`).
   - Executed first during framework installation.
2. **Plugin Migrations** (`plugins/webkul/<plugin>/database/migrations/`):
   - Owned entirely by the domain plugin module.
   - Loaded dynamically via `$this->loadMigrationsFrom(...)` in plugin service providers.
3. **Alteration Migrations**:
   - Plugins that extend existing tables owned by another plugin create targeted alteration migrations:
     - Example: `plugins/webkul/payments/database/migrations/2025_02_12_103602_add_columns_to_account_payments_table.php` alters `accounts_account_payments` to add payment transaction reference columns.
     - Example: `database/migrations/2026_07_21_100000_add_company_id_to_settings_table.php` alters `settings` table.

Evidence:
- `database/migrations/`
- `plugins/webkul/payments/database/migrations/2025_02_12_103602_add_columns_to_account_payments_table.php`
